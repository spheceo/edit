# Codebase audit — 11 October 2026

This review covered the project model, frame evaluation, GPU compositor, WASM
bridge, browser playback and timeline, saves and undo, local API/MCP, uploads,
FFmpeg jobs, exports, script downloads, transcription, agent bridge, self-update,
release configuration, and relay. Findings were checked with regression tests,
a real Chrome/WebGPU session, an isolated native server, and dependency scans.
This is a repository review and targeted runtime verification, not an external
penetration test or a performance certification across every codec and device.

Changes are in the working tree. No release, production deployment, or user
project migration was performed.

## The two reported problems

**Refresh lost the playhead.** The editor explicitly reset the frame to zero,
and playback never persisted it. Positions are now stored per project in browser
storage. Explicit seeks, pauses, project switches, page hide and detach checkpoint
immediately; playing checkpoints at most once a second. Restoring happens before
the first project render, and the timeline centers on the restored position.
Blocked/full storage cannot crash editing. This preference is specific to the
browser and origin; it does not synchronize between devices.

**Cuts could briefly show the wrong picture.** `HTMLVideoElement.currentTime`
can reflect a seek before the new picture has decoded. The preview also allowed
incoming rolls to show footage before their source in point. Playback now tracks
decoded picture presentation with `requestVideoFrameCallback`, coalesces seeks
to their latest target, avoids copying unsettled pictures, and holds the previous
complete scene until every required incoming picture is ready. Upcoming moments
are cued separately, with a smaller alignment bias. Loading feedback appears
after 150 ms, avoiding a flashing indicator for normal short seeks.

The real-browser test uncovered another bug: ending playback scheduled a final
animation callback but left its ID recorded indefinitely. Every later paused
scrub was ignored. The loop now clears its ID on entry and schedules another
callback only while still playing. A regression test covers this case.

Severity below describes impact in this application's local/trusted-tailnet
deployment, rather than a formal CVSS score.

## Remaining risks and next work

### P1 — Financial limits on the shared public relay

Atomic reservations close the concurrency hole, but byte quotas do **not**
guarantee a monetary spending limit for arbitrary uploaded audio. The public
endpoint accepts client-supplied audio; compressed duration is not proportional
to file size. Even Edit's own default VBR encoding produced a 60-second silent
recording of **28,794 bytes**, versus 240,000 bytes at a constant 32 kbps.

Private relays can now use `CLIENT_TOKEN` plus native `EDIT_RELAY_TOKEN`.
The shared public service needs verified audio duration before forwarding paid
requests, an upstream account spending limit, and an abuse/identity policy.
An embedded common token in a public binary would not establish client identity.
Use duration reservations after verification; decide refunds using confirmed
upstream outcomes rather than ambiguous network failures.

The Durable Object binding/migration is configured and dry-run verified, but
**has not been deployed**. Deploy at a UTC quota boundary or seed the new day's
balance from existing usage so switching from KV does not grant a second day's
allowance. Existing KV resources were not deleted.

### P1 — Preview/export audio and timebase parity

Browser media-element rates are still clamped to 0.0625–16 while the model and
export support 0.05–20. Media-element volume is capped at 1, so positive dB boosts
cannot match native export. Identical audio moments on multiple tracks also need
explicit mixing semantics. Short effects now have fades, but mixed overlapping
fades and long-clip audio need sample-level comparison.

Route long audio through Web Audio gain nodes and use the AudioContext clock for
scheduled audio. Exercise 24/25/29.97/30/60 fps combinations, variable frame rate,
rotation, source EOF, speed extremes, overlapping audio, proxy switching and
long sessions. Proxy CFR/time-index decisions must map original presentation
timestamps explicitly. Shared compositing ensures effect parity; it alone does
not prove source-decoder, audio or HDR parity.

### P1 — Crash/offline draft recovery

The last drag gets a save opportunity and unsaved navigation receives a warning,
but unload callbacks cannot guarantee completion, and a process crash can lose
debounced edits. Add an IndexedDB draft or operation journal before sending a
save. On reopen, compare its base revision with the server, offer recovery, and
clear it only after acknowledgement. Expose a small Saved/Saving/Offline state.
Directory fsync and recovery of abandoned temporary files should be considered
if power-loss durability is part of the storage contract.

### P1 — Explicit remote trust boundary

Origin/Host defenses protect against hostile webpages; they do not authenticate
programs or other authorized tailnet peers. The API intentionally exposes local
filesystem browsing, imports, rendering and agent access. Keep it behind trusted
localhost/Tailscale ACLs. Multi-user or public hosting requires authenticated
sessions/tokens and filesystem capability boundaries, including MCP, WebSockets
and update/agent endpoints. This audit did not change that product trust model.

### P2 — A faster scrub pipeline

1. **Bounded decoded-frame cache.** Cache around the current frame, recent seeks
   and upcoming cuts, keyed by source/version/time. Render a cached picture
   immediately while decoding the precise latest target. Evict by bytes and close
   every `VideoFrame`: one 1080p RGBA picture is about 7.9 MiB, so frame-count-only
   limits can waste substantial memory. Start with a 64–128 MiB budget and measure.
2. **Worker decoding and rendering.** Prototype WebCodecs with indexed/demuxed
   proxies and an explicit presentation-time map. Keep HTML video as a capability
   fallback. Move expensive work away from pointer input, retain latest-request
   coalescing, and verify audio sync/device-loss behavior before replacing the
   current pipeline. WebCodecs alone does not provide MP4 demuxing.
3. **Adaptive preview resolution.** Render a reduced-resolution interaction
   preview during fast scrubs/drags, then settle at full resolution after input
   stops. Preserve the shared renderer and scale text/effect radii consistently;
   silently changing only the browser shaders would break parity.
4. **Priority preprocessing and progressive availability.** Prioritize the
   visible source and near cuts over background imports. Generate a quick proxy
   tier or independently playable chunks so a long recording need not finish one
   full all-intra encode before fast scrubbing becomes available. Version caches
   when proxy policy changes. Current jobs are bounded but not visibility-aware.
5. **Performance instrumentation.** Measure input-to-present p50/p95/p99, decoder
   queue age, held/dropped pictures, cut readiness, GPU upload bytes, export fps,
   and memory after many project switches. Test 10/1,000/10,000 clips and local vs
   tailnet access. Set release thresholds from a measured baseline; no universal
   10 ms seek claim is justified by the current tests.

### P2 — Native export throughput and user experience

GPU readback buffers are reused now, but export still waits synchronously for
readback and pipes RGBA to a CPU encoder. Benchmark a small asynchronous readback
ring and supported hardware encoding against the current quality/output. Reuse
sequential decoders across continuous splits without merging simultaneous source
moments. Add a global export resource budget and timeouts/cancellation around
blocked decoders, not only checks between frames.

Persist/export job status so reloading can reattach to progress. Add actionable
missing-media relinking, cache size/cleanup controls, automatic failed-proxy retry
with clear errors, and chunked/resumable remote uploads. Long transcription jobs
would benefit from timed chunks and explicit external-service/cost information.
The model's image kind is not a complete image-import/preview feature yet; either
implement it end-to-end or keep it out of advertised capabilities.

### P2 — Dependency and startup maintenance

`cargo audit` found no known vulnerability entries in 216 locked packages, but
reported **RUSTSEC-2026-0192: ttf-parser 0.25.1 is unmaintained**, pulled through
fontdue. Current rendering uses bundled fonts; evaluate a maintained replacement
while preserving font metrics and pixel parity before adding user fonts. Bun's
web dependency audit returned no advisories. These results reflect the advisory
database available on the audit date, not proof that dependencies are vulnerability-free.

The production web build still warns about a roughly 621 kB JavaScript chunk
(about 196 kB gzip), alongside the WASM download. Split optional agent/transcript/
graph features, show startup progress, and profile first usable preview on a
remote connection. All-intra proxies also need an explicit disk-space policy.

## Verification and reproducibility

- `just check`: formatting, native/wasm clippy with warnings denied, Rust tests,
  TypeScript checking and frontend tests: 42 Rust tests and 24 frontend tests
  passed; one existing external Drive test remained ignored. All four GPU tests
  ran on this machine, including 600 independent draws beyond the former limit.
- `just wasm` and production web build completed.
- Real Chrome/WebGPU fixture: red frames 0–19, blue frames 20–39; **zero incorrect
  rendered pictures and zero black samples**, including seeks after natural end.
  Instrumented seeks took about 49–51 ms on this synthetic 320×180 fixture. Rapid
  requests ended on frame 5; reload restored frame 5 in the harness and editor.
  This instrumentation reads pixels and is not a general performance benchmark.
- Native export: 40 frames, 320×180, 30 fps, duration 1.333333 seconds. Decoded
  output frames 19/20/21/39 were respectively red/blue/blue/blue. Separate failed
  and cancelled exports preserved sentinel destination files and left no partial
  output; exporting over source footage was rejected.
- Runtime request checks: hostile Origin, null Origin, cross-site fetch metadata
  and an unrelated `.ts.net` Host returned 403. Matching Origin and CLI requests
  without Origin succeeded.
- Wrangler deployment dry run succeeded with the Durable Object binding and
  migration. A regression tests concurrent daily reservations; live paid upstream
  requests and production deployment were deliberately outside these checks.
- A local HTTP relay mock received the private bearer token correctly. Two
  concurrent native transcription requests made exactly one upstream request.
  Exporting through the actual editor dialog completed successfully, and the
  browser reported no console warnings/errors during the final UI check.
- Added browser fixture generation and instructions in
  [`web/tests/README.md`](../web/tests/README.md), plus unit regressions for
  restoration, settled seeks, deduplication, proxy changes, playback end,
  invalid drags, stale saves, conflict recovery, mutation retries and relay quotas.

Long user recordings, all supported browsers, adverse network conditions and HDR
were not comprehensively exercised. The existing external Drive download test
remains ignored; confirmation parsing, concurrent local excerpts and protocol
restrictions received local verification.
