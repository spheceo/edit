# The server in Effect, where the same bugs keep coming back

Sphe, Nov 1: after Mathias's two FOIA scripts stopped at "transcription failed (413)" (a 4 h 39 min and a 5 h interview, each import ~41 min before it failed and then resumed 13 times), "if the import stage was written in Effect… would we have prevented this?", then "look at the last maybe 400 commits… which were bug fixes that we came back to more than once, and rewrite those parts of the code in best practice Effect. take your time with the rewrite."

The answer to the first question was: not the mismatch itself (the client sends a whole file at 32 kbps, the relay caps a request at 45 MB, nobody joined the two numbers), but everything around it: the error would have been a type the import had to handle, retries would never have been offered for an error that can't change, the pieces would have been interrupted when the whole hearing failed, and the trace would have said which step took the 41 minutes.

## How the rewrite is done

- Effect 4 (`effect@4.1.1`, `@effect/platform-bun@4.1.1`), written as the package's own AGENTS.md teaches: `Effect.fn("name")` for functions, `Schema.TaggedError` for every failure, `Context.Service` / `Context.Reference` for what a part needs, `Schedule` for every retry, `Effect.forEach({ concurrency })` / `Semaphore` for "N at once", `Scope` and `effect/process` for child processes, so interrupting the work kills its processes.
- Part by part, inside the module, keeping its exported Promise functions with the same names, arguments, results and error messages, so callers (and their tests) don't change. Effect stops at that boundary until the callers are rewritten too; then the facade goes.
- One runtime for the server (`src/effect/runtime.ts`): the platform layer and a logger that writes Effect's logs through `diag`, so lines keep landing in `edit.log` and the problem reports.
- Every error says whether asking again can help (`retryable`). The Promise boundary turns it into the same `Error` text the UI and the log have always shown, so the UI can stop offering Retry for an error that can't change (part 6).
- Each part: the rewrite, the module's tests passing unchanged (plus tests for what was the bug), `just check`, one commit.

## Order

1. **Transcription**, with Nov 1's fix: errors typed (busy, gateway down, unreachable, allowance used up, too long for one request, refused, extract failed); one retry schedule per kind; the pieces and the whole hearing run together and either failing interrupts the other (and kills its FFmpeg); the whole hearing is encoded at a bitrate that fits the relay's limit (a test reads the limit from `wrangler.toml`, so the two can't drift again), and a file too long even for that keeps its words from the pieces and goes without voices rather than stop the import.
2. **Sign-in renewal**: the renewal policy as one `Schedule`, the token refusals as typed errors.
3. **Child processes**: one `Proc` service (`effect/process`), every FFmpeg/FFprobe/yt-dlp of parts 1, 3 and 6 through it, owned by a scope; limits as semaphores.
4. **Downloads**: the route ladder as data, failures typed as "the video is gone" (stop) or "this route failed" (next route).
5. **Script cloud sync**: one script's failure is that script's state, said once, not a warning each pass; the loop is a supervised fiber.
6. **Script import**: steps as Effects with typed failures; Retry offered only when the failure is retryable; resume never re-runs a finished step.
7. **Exports, shares, archives**: a file being read is held by a scoped lease; an archive waits for the leases.

## Round 2: every outside call

Sphe, Nov 1: "We want more of the TypeScript backend (app/apps/server) rewritten in Effect, beyond transcription. Prioritise the areas where things can go wrong and already have." In each area:

- every outside call (Scribe, Drive, R2, the relay, Modal, FFmpeg) has a typed error and a Schema-checked answer;
- only temporary errors are asked again, and Try again follows the same split;
- work limits, timeouts and cleanup go through scopes;
- tests with fake services for the bad days: a 413, a 429, a slow R2, a timeout.

One area at a time, its tests green, its Promise interface to the rest of the code kept, committed before the next.

First, shared by all of them (`src/effect/service.ts`): what can go wrong with any outside call (`ServiceUnreachable`, `ServiceTimedOut`, `ServiceRefused` with its status and Retry-After, `AnswerInvalid` when the answer doesn't match its Schema), and the one rule for each error's kind (`kindOf`): **temporary** (a dropped connection, a timeout, 408, 429, 5xx: Edit asks again itself, on a schedule), **later** (a person can change it: the day's allowance, a sign-in, a quota: Try again is offered, Edit doesn't loop on it) or **permanent** (the same build gets the same answer: Try again isn't offered until an update). Each area's own errors are given a kind in the same table.

The order:

1. **Scribe and hearing**: the Scribe answer through a Schema, a request timeout as its own temporary error, `writer/hearing.ts`'s stretch cut through a scope, and the import's Try again (`stuck`) read from `kindOf`.
2. **Writer imports and Drive downloads**: Drive's API calls and the Drive-to-R2 copy (`drive.ts`, `writer/drive.ts`, `writer/streamed.ts`).
3. **Cloud sync and conflicts**: the Convex calls through the relay and what a commit can answer (a conflict, a lock someone else holds, offline, refused) as types; the sync loops' backoff by kind.
4. **Child processes and long jobs**: FFmpeg and FFprobe runs (`media.ts`, `tools.ts`) through `effect/proc.ts` with timeouts; `jobs.json`'s restarts.
5. **Sign-in and token renewal**: the accounts site's token, device and revoke answers through Schemas.
6. **R2 and the relay**: `relay.ts` and `cloud.ts`'s R2 transfers: typed errors, only temporary ones retried (the old `retry` asked again after any refusal), stalls as timeouts.
7. **Renders and exports**: the Modal export driver's calls (`modal_exports.ts`, `cloud_exports.ts`) and the export's FFmpeg join.

### Round 2, done

- Area 1, Scribe and hearing: `src/effect/service.ts` (the shared errors, `kindOf`, `temporaryRetries`, a timed `request`, Schema decoding); Scribe's answer read through a Schema (one that isn't Scribe's is `AnswerUnreadable`, permanent, said at once); a request past `RequestTimeoutMs` is `RelayTimedOut` and asked again as the gateway is; every transcription error given its kind; `writer/hearing.ts` in Effect (the stretch's FFmpeg and file owned by the hearing's scope; a stop ends both and the request); the import's Try again (`stuck`) is `kindOf(error) === "permanent"`. Tests: `test/service.test.ts` (503, 429 with Retry-After, 413, 400, a slow service, an answer that doesn't match), `test/transcribe.test.ts` (a slow relay, a 200 that isn't Scribe's), `test/writer/hearing.test.ts` (a stop mid-hearing).
- Area 2, Writer imports and Drive downloads: `writer/drive.ts` in Effect. Drive's listing and metadata calls are timed (60 s), read through Schemas (a file, a file list, a folder), and asked again only when temporary; refusals are typed and given kinds (`DriveNotShared` later: someone shares it, then Try again; `NotRecordings` permanent: Replace, not Try again; `DrivePage` later). The download resumes from its bytes at each try (four more), abandons a connection that sends nothing for `STALL_MS`, and now treats an answer that ends before the recording does as a dropped connection: the old loop took it as finished and came down short without asking again. Out of tries it's `DownloadShort` (temporary: Try again carries on), which the import reads by its tag, not its words. Drive's calls go through `endpoints.google`, so tests stand a fake Drive in (`test/writer/drive_bad_days.test.ts`: a 503, a 429 with Retry-After, a 404, an answer that isn't Drive's, a connection closed half-way, a stall, a 403, short after every try). The Drive-to-R2 copy (`writer/streamed.ts` → `cloud_media`) is R2's, area 6.
- Area 3, cloud sync and conflicts: the relay's JSON call is an Effect (`relay.ask`, `relay.askJson`: timed; a dropped connection and a timeout both "could not reach Edit's relay", what the loops read as offline; a 401 with a person's token renewed once; a refusal in the relay's words; the answer checked against a Schema), and `relay.json` is its facade, so every caller has it. The Convex call (`cloud.convexEffect`) reads Convex's answer through a Schema (`ConvexAnswer`) and fails with `ConvexFailure`, now tagged and given kinds: unreachable or slow temporary, the database paused for a move "later", a conflict or a lock "later" (the sync's to settle), anything else by its status or permanent. A query is asked again after a temporary failure; a mutation never is (its answer may have been lost after it landed). Script mode's sync reads the same envelope Schema, and a script the cloud fails for a moment (a 5xx, 429) waits its first backoff and goes again instead of being kept as a refusal ("Not in the cloud") with a doubling wait. Tests: `test/cloud_bad_days.test.ts` (a 503 and a 429 on a query, a 503 on a mutation, a slow relay, the pause, an answer that isn't Convex's, a conflict).
- Area 4, child processes and long jobs: `tools.run` (about 25 FFmpeg and FFprobe callers: review copies, posters, watermarks, waveform PCM, excerpts) is a facade over `tools.runTool` on `effect/proc.ts`'s new `capture`: the tool's whole process group is the run's, ended when its time (`TOOL_MS`, 4 h, or the caller's) runs out or the work around it is interrupted (callers can now pass a `signal`), with the same words for a failure (its last line) and a missing FFmpeg. Process failures have kinds: one that ran past its time is temporary; one that failed is read from its last words (`proc.failureKind`: a dropped, reset or timed-out network read and a 5xx from the server read are temporary; a damaged file, a missing stream or a bad option permanent), and Script mode's `writer/proc.ts` errors read the same way. `jobs.resume` starts each cut-off job with a time limit (`RESUME_MS`, 60 s): one still starting is left running and the others go on, where one that hung held up every other. Tests: `test/tools_run.test.ts` (output as bytes, a failure's last line, a missing tool, a stuck tool ended with its child, a stop, the kinds, a hanging resumer). On the way: an idea's run was dropped from the running list before its ending was saved (`ideas/run.ts`), which a look in between saw as not running but still "running"; fixed in its own commit.
- Area 5, sign-in and token renewal: every call to the accounts site (`accounts.ts` `postEffect`: `/app/token`, `/app/device`, `/app/revoke`) is timed (`ACCOUNTS_MS`, 20 s) and read through a Schema of what the site sends; a success that isn't its answer is `AnswerInvalid`, an error page that isn't JSON reads as an empty answer with its status, and a sign-in is taken only from an answer with both tokens (`Granted`). The renewal attempt calls it directly (its failures stay `RenewalFailed`, asked again by `renewalRetries`; only `invalid_grant` signs out). The device sign-in's polling is one Effect loop on unref'd waits (pending, slow_down, a 429's Retry-After, a dropped connection asked again while the code lasts), and a sign-out the site's limit refuses is revoked again on the runtime after its Retry-After. The authorization code's exchange is asked once: the code works once. Tests (`test/accounts.test.ts`): a token call too slow, a 200 with no tokens, a 502 page (each kept signed in and said), a refused revoke done again.
- Area 6, R2 and the relay: every R2 failure in `cloud.ts` is typed and has its kind: R2 unreachable or a transfer stalled (said as a timeout) temporary, a refusal by its status (`ServiceRefused`: a 403 "later", a 5xx or 429 temporary), a file changed under a transfer, R2 storing a different size, a range past the object or a server ignoring the range (`TransferMismatch`) temporary, an answer missing what the relay always sends (`AnswerInvalid`) permanent. `cloud.retry` (every single PUT, every part and every download) asks again only after a temporary failure: it asked again after anything but a bug, so a refused upload took four tries and 14 s to say so. Its waits stay on `timing.sleep`, and the stall and connect limits are on `timing` too, so tests can make R2 slow. `relay.call` (answers written to a file) is on `relay.ask` now, and the old `send` is gone: every relay call goes through the one timed, typed request. The Drive-to-R2 copy (`cloud_media.driveOriginal`) uploads its stream's parts through the same `retry`. Tests (`test/r2_bad_days.test.ts`): a 500 on an upload, a 403 on an upload (once), a 429 and a 403 on a download, an R2 too slow to answer, and the relay slow, busy, answering what isn't JSON, and refusing a file (413).
- Area 7, renders and exports: `modal_exports.ts` in Effect. A job through the relay (`throughRelay`) reads its start and status answers through Schemas and is asked every `timing.pollMs` until it's done, failed (`ModalJobFailed`), cancelled, or past `timing.deadlineMs` (then cancelled in the cloud; it used to poll for ever); a status failing for a moment (offline, a 5xx, a 429) is waited out until it has gone unanswered for `timing.statusLostMs` (`ModalUnanswered`), any other failure is said at once; a cancel, or the export being interrupted, cancels the job in the cloud. The local driver (`driving`: Infisical, uv and the Python driver) is one process group the run owns, ended by a cancel (which still leaves its cancel file), a failure or the deadline, where a SIGTERM to Infisical alone might not have reached the driver; its JSON lines are read through a Schema. `cloud_exports.ts` reads the relay's start and status answers through a Schema and stops at once on a permanent status failure (anything else is still waited out: a lost answer never starts a second paid render). Tests (`test/modal_bad_days.test.ts`): a job not started, a status lost for a moment, a 403, a failed job, a status gone too long, a job past its deadline, a cancel, and the local driver's lines, error and cancel ending its group. Not here: the export's own FFmpeg join is the Rust engine's (`crates/edit-engine`), outside the TypeScript server.

All of round 2: the server's 1,021 tests (1,015 pass, 6 skip), typecheck (apart from the other session's `src/ideas/` work in progress, at times) and lint.

## Round 3: the code around them

Sphe, Nov 1: "let's make the surrounding code effect" and, of the merge rules Effect can't catch, write them so they can be checked.

- Which copy wins a Script mode pull is one pure function (`writer/cloud.ts` `decidePull`), and `pullOne` does what it says. Its promises are property tests over 2,000 generated pulls each, with Effect's own `Arbitrary` (`test/writer/merge.test.ts`): work changed here is never lost, a built script is never replaced by an unbuilt one, at most one conflicted copy per revision, an older or equal revision is never taken, a script deleted elsewhere after it changed here is kept as a restored copy, a body missing from the cloud never replaces this Mac's. Removing the built-script rule fails its test with the smallest case that shows it.
- Edit mode's project sync: what a failed call leads to (`cloud_projects.ts` `decideFailure`: offline, someone else's turn, take the lock again, a conflict, an error), whether a conflict is this machine's own lost save (`isOwnSave`, 8f67a6cf) and what losing the lock does (`afterLost`) are pure and property-tested (`test/cloud_merge.test.ts`): offline is only ever offline, this machine's lock is never someone else's, a conflict is taken as its own save only when the cloud's next rev is exactly what it sent, losing the lock with changes here always keeps them.
