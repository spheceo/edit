# Edit audit, 8 Nov 2026: playback and the loose ends

Sphe, Nov 8: "a full audit of the codebase… one of the biggest things we haven't been able to crack as yet is really smooth playback… we sort of have these various webs branching out in the app… I need us to tie up all of those loose ends." Scope is agreed here first; then one Opus 5.5 sub-agent per item in section 4 does the work, playback first. Nothing in the code was changed for this audit.

## The short answer

Playback isn't the cloud footage as such and isn't one bug. Four playback systems were built in one month (live WebCodecs decode of R2 proxies, Modal renders, Mac smooth renders in chunks, the Nov 6 native player); three still run; and the one that could be Premiere-smooth, the native player, has a design gap (no decode-ahead, the page drives it frame by frame, sound still in the page) and almost nobody is on it. Sphe's own Mac has never used it: nightly-67 runs from a scratchpad bundle with no `/Applications/Edit.app`, the window had no click in 31 hours, and the team's traffic is browser tabs on the page player. Only JJ's Mac showed the native player on Nov 8, and there it looked fine. Meanwhile "footage stays on the Mac" isn't happening on Sphe's Mac (0 bytes of local proxy copies; the cleaner evicts them for 8.7 GB of export chunks on a 93%-full disk), so every frame streams.

The webs share one pattern: state that matters lives in memory with a checkpoint file beside it; fallbacks stand in for diagnosis; shared resources (the hardware encoder, the uplink, the lock, "is this Mac busy") have no owner; timers were set independently; and every rebuilt feature kept its predecessor.

Paths are relative to `app/`. "Confirmed" = read in the code and consistent with logs; "likely" = read in the code, not run; "uncertain" = flagged by a reader, not verified by me.

## 1. Playback (the main complaint)

### What exists today, on a Mac

| Path | Where | Decodes | Clock | When used |
|---|---|---|---|---|
| Native player | `crates/edit-engine/src/player.rs`, `crates/edit-window/src/preview.rs`, `apps/web/src/lib/nativePreview.ts`, `apps/server/src/native_preview.ts` | AVFoundation, per frame, synchronously on one thread | the page's AudioContext | Edit.app, not full screen, until 5 failed frames |
| Page live preview | `apps/web/src/lib/playback.ts`, `decoder.ts`, `decode.worker.ts`, `range-source.ts` | WebCodecs in workers, through the server's block cache | AudioContext | browsers, Linux, full screen, after native fails; **and always for sound** |
| Smooth render, streamed | `playback_render.ts`, `playback_stream.ts`, `lib/smoothStream.ts` | background export in chunks → MediaSource + `<audio>` | the `<video>`'s | page path when a render exists for the rev |
| Smooth render, whole file | same + `<video src>` | | the `<video>`'s | R2 renders (Modal-era) |
| Scrub tier | `scrub.ts` + `playback.ts` `scrubbed()` | all-intra 960×540 pieces | | page path while dragging |
| Script-mode player | `apps/web/src/writer/playback.ts` | shared decoder | its own | Script mode |

Confirmed findings:

1. **The native player has no decode-ahead and the page still drives it frame by frame.** `Player::draw` (player.rs:150-180) evaluates the scene, decodes every layer's picture synchronously (`PreviewPictures::decode`, render.rs:1075-1120, 1 thread for ≤2 layers), uploads, renders, presents, then answers the Tauri IPC call. The page asks for the next frame only when the last answered (`drawNative`, playback.ts:455-479). Any frame that takes longer than 33 ms (a cut to a new file = new `AVAssetReader` via `restart`, mac_media.m:283; a jump; a cloud stream) is a visible hitch, and the audio clock runs on so frames are skipped. Premiere pre-rolls upcoming cuts on other threads; the export pipeline in render.rs already does (planner → 3 decoders → compositor), but the player doesn't use it.
2. **Two clocks, two decode pipelines for one viewer.** Picture is native; sound is still decoded in the page by WebCodecs from HTTP range reads of the same proxy (`tick()` playback.ts:880-915 gates play on `audioReady`). So in native mode "Loading frame…" can still come from the sound path, and the sound path keeps every failure mode the page player had (hung worker replaced after 10 s, decoder.ts:23; 4 s decode retry; range retries).
3. **Cloud footage imported on another Mac scrubs at 3–8 s a frame until whole copies land.** `native_preview.ts:30-41`: a proxy not yet local is streamed by FFmpeg over the loopback `PLAYBACK_ROUTE` (a new stream per jump) while `fetchWhole` downloads it, 4 at a time (local_previews.ts:27). JJ's log today: 6 s to 4 min per file. A project with 30 excerpt proxies is painful for tens of minutes; the page re-asks every 15 s (playback.ts:431-437) and on each change `pictures.clear()` reopens every reader. This is the review-fixing case (JJ imports, Mathias or Sphe fixes).
4. **Full screen silently starts a background render of the whole edit.** F → `setNativeAllowed(false)` → `leaveNative` → `native=false` → Viewer's effect (Viewer.tsx:117-125) asks `renderPlayback` after 2.5 s because `playback.state` is "none" in native mode. That render takes a place in the export line (`takeTurn`) and the one hardware encoder. Likely; confirmed by reading, not run.
5. **Every project change is re-sent whole to the window.** `syncNative` (playback.ts:445-452) sends the full project JSON (2–2.5 MB for current prod projects) through Tauri IPC once per frame while anything changes; `set_project` (player.rs:105-140) re-parses and re-`validate`s it on the player thread, which also decodes. Dragging a clip on a big edit is likely laggy in Edit.app for this reason. Needs measuring on the Mac (the Nov 6 measurement was scrub and play, not a drag).
6. **The same proxy bytes are kept on disk in up to four forms** on one Mac: 2 MiB blocks (`cloud_blocks.ts`), whole copies (`local_previews.ts`), 30 s excerpt cells for smooth renders (`export_excerpts.ts`, `edit/excerpts/proxies/…`), and 5-minute scrub pieces (`scrub.ts`), each with its own fetcher, cleaner and failure path. Now that footage stays on the Mac (Nov 6 step 2), the whole copy is the only one the native player needs.
7. **Store churn on media status.** Each `media` websocket event clones the whole media map and `setState`s (web store.ts:644-650); Marc's Mac logged 503 such updates in a quarter second, repeatedly. Viewer recomputes a JSON key over all media per update (Viewer.tsx:74-84) and re-sends the project to the engine and the window when the key changes. Likely one source of the 1.6–1.9 s "page was stuck" lines.
8. **Timing constants in this web, each in its own file:** 150 ms slow badge, 600 ms badge, 10 s stuck, 4 s decode retry, 10 s hung worker, 300 ms settle, 150 ms drag gap, 2.5 s smooth settle (Viewer), 45 s after-turn render, 600 s auto-render cap, 15 s native-source re-ask, 10 min fetch retry, 5 native failures, 20 s/2 min stream window. None are measured against each other.
9. **No automated test covers the native path** (no test references `preview_frame`, `Player`, or `nativePreview`); the only check is the manual `EDIT_PREVIEW_CHECK` run.
10. The encoder is shared by exports, smooth renders, exports made ahead, review copies, proxies, scrub pieces, writer preview pieces and RIFE smoothing. Only engine-spawned FFmpeg pauses for an export (media.rs:353-418); Node-spawned FFmpeg (`tools.run`: review copies, proxy pieces, writer pieces, RIFE) never does. JJ's export took 41 min while 56 writer preview pieces encoded beside it, and the writer's pace judge (writer/media.ts:150-175) then killed pieces as "too slow" because it has no idea the encoder was busy. Two imports stopped that way today.

### Direction (already agreed on Nov 6, not yet built)

One native clock; a decode-ahead ring (reuse the export's planner/decoder threads); sound in native (CoreAudio) or at least the page's AudioContext following a native position; the page sends only deltas (or the window reads the saved project and takes patches); whole local copies as the one footage form, prefetched in playhead order when a project opens; the smooth-render, scrub-tier and block-cache paths retired on the Mac (kept behind the browser/Linux path until that's measured). Measure first on the Mac: a clip drag on a 2 MB project, a 30-cut stretch of playback, and the review-fix case (JJ's project opened cold on another Mac).

## 2. The webs (other flows)

### 2a. Import (script → footage → proxies → transcription → voices → layout)

Confirmed by spot-check: the script job lives only in memory (`script.ts:1278`); `waiting` (a file missing) ends the durable jobs.json entry (`script.ts:2051-2057` + `finally` at 2145), so a restart during "waiting" leaves an empty edit with no Waiting panel; `MOST_RESUMES = 2` (`jobs.ts:37`) silently abandons a job after two restarts while the page's own resume heuristic (`web store.ts:548-556`) still fires; the transcription wait gives up after 30 min and lays out without words silently (`script.ts:2507`).

Other paths from the reader (file:line in the agent report): `runTool`/`cut`/`makeProxy` have no timeouts so a hung FFmpeg keeps the job RUNNING, which blocks Retry/attach/skip (`script.ts:1644`, `cloud_media.ts:1271,1289,1385`); relay DriveToR2 polled with no overall deadline (`cloud_media.ts:1141-1163`); a voice-over failure marks a laid-out, playable edit as a failed import (`script.ts:2110-2120`); Drive folder import downloads inside the HTTP request with no progress (`drive_import.ts:79-83`); pieced-proxy failures fall back silently to whole proxies; `statusFromDisk` says `proxy: ready` for any streamed path even when the key 404s (`media.ts:192-195`) → "Loading frame…" with only "Stuck? Report it".

Operational: the ElevenLabs quota ran out today and four imports on two Macs stopped as errors needing a manual Retry; nothing told Sphe; nothing queues them to resume when credit returns.

Structural: job state in memory with progress as a side channel; two footage pipelines (disk and cloud) with different stall timers and retry regexes (`passing`, `script.ts:63`); four proxy/upload kinds (whole, pieced, own-file, backfill/uploadLater); no wall-clock bound inside RUNNING; the import's done/failed coupled to follow-on work (voices, research prompt).

### 2b. Cloud sync, locks, restarts

Confirmed by spot-check: the lock is released after 60 s with no write even with the editor open (`cloud_projects.ts:70, 215`); revisions start from a random base each server start (`store.ts:124`); `store.update` (every tool but `apply_edit_plan`) only asks `mayWrite`, never a rev (`store.ts:461-470`).

From the reader: the next keystroke after the 60 s release blocks on a network claim and can 423, and the page then takes the live project without pushing that edit to undo (`web store.ts:418-430`); the default holder name is the computer name, so two Macs named alike both hold the lock and fork silently (`cloud_projects.ts:429-433, 1192-1200`); a push whose answer was lost at quit comes back as a spurious conflicted copy (attempts are in memory, `1348`); take-over propagates in up to 45 s during which A's agent keeps writing; **Writer scripts have no lock at all** (`writer/cloud.ts`: push 2 s, pull 30 s, copy on any overtaken commit), which is the stream of "(conflicted copy)" scripts (9 visible today); a page open across a restart may ignore server changes until it edits if the new random base is lower (uncertain); rebase is item-level last-writer-wins and Undo after a dropped rebase saves the whole old project over the other party's changes (`web store.ts:185-201, 275-281`); `resumeInterrupted` resumes an agent turn without asking `mayWrite` and has no resume cap; the quit budget is 5 s while one Convex call may take 15 s (`serve.ts:281` vs `cloud_projects.ts:76`).

Structural: two sync systems with two conflict policies (projects: lease lock; scripts: optimistic, no lock); revisions that don't survive restarts; five independent "is this busy / who may write" answers (`workingHere`, `busyWith`, `reviews.busyHere`, page `readOnly`, `permission`); lock lifetime tied to writes not presence; four durable-work ledgers (`jobs.json` resume ≤2, `running-turns.json` resume forever within 10 min, `retry-after-update.json` once per build, `export-failures.json`).

### 2c. Export → Share → Review → Ready for changes → fix → re-share

Confirmed by spot-check: the Share dialog shows "Up on the link" on the export's `done` event (`ShareDialog.tsx:310`), before the copy/upload/publish, whose failures reach the dialog only via polling; the review copy is checked by lengths only (`review_check.ts:45-51`), which is how Female Police Captain v2 shipped undecodable on Nov 7; `busyWith` (`remote_actions.ts:438-455`) lists exports but not a share's copy/upload, so an idle update can cut a share; the share's export starts without `keepLocal` (`reviews.ts:701`) though AGENTS.md says it's kept.

From the reader: the engine's fallback chain (chunked with reuse → chunked without → whole native → whole FFmpeg, `render.rs:1634-1692`) hides the first cause and costs an hour before anyone sees it (Marc's Mac: 7 chunk-join frame-count mismatches); the stall watch restarts the same inputs 3× (`exports.ts:1015-1034`); pre-engine prep (excerpt cuts, fetching the last archived export back) has no stall watch; the export is uploaded to R2 twice (archive job + `fullBehind`) on one uplink; a restart mid-share after the export's job ended resumes nothing and sets no `unshared` (user Share path); claimed notes can be held 30 min and given up after 2 tries (`reviews.ts:67-69, 992-1000`); disk room is checked once at start; smooth playback renders take a place ahead of exports with no stall watch; exports made ahead run on whichever Mac edited last, fetch gigabytes of the archived export back, and change every chunk key when the watermark differs.

Duplicates: 4 export lists, 4 progress estimators, 5 "busy" rules, 3 replace-vs-next computations, 2 review-copy checks (one in the worker), join integrity only for export chunks not review pieces, 4 retention rules, 2 upload-resume mechanisms.

### 2d. Agent turns

Confirmed by spot-check: `MainAgentPanel` subscribes to the whole agent store unselected (`AgentPanel.tsx:218`) and rebuilds turns every render; the composer's queue effect sends the next queued message synchronously when `running` flips false (`ChatComposer.tsx:122-137`), racing Edit's own 1 s follow-up (`agent.ts:1405-1419`), so one of them fails with "still working"; `store.update` tools never conflict with hand edits; the chat path never waits on the plan limit before starting (`planLimit.room()` is only in `claude.ask`).

From the reader: a stale `apply_edit_plan` is refused whenever the user hand-edits mid-turn (13 today on Marc's Mac), while every other tool silently wins over hand edits (page rebases and drops); any non-"busy" error ends a turn half done with no follow-up (follow-ups only on `error === null`); a hard crash leaves the old `claude` process calling the new server's `/mcp` beside the RESUMED turn (no stray-process sweep for Claude); sub-agent cards stuck on "Stopped" after a restart (`subCards` in memory); notes on the player marked "sent" and orphaned if the server restarts within the 5 s requeue poll (`edit_notes.ts:234-249`); tool errors are deliberately greyed in the UI so a turn looping on a locked project looks like "Working for 12m"; the 25-min watchdog is fed by stream events so a hung 15-min MCP call holds "Working" ~40 min; error class is inferred from result text by regex (`busyModel`, `isLimit`, "no conversation found"). React #185 at turn end: the synchronous `setState`-in-effect chain (`useQuiet` per turn × N, the composer queue effect flipping `running` back inside the same commit) is the plausible suspect; not pinned statically.

Duplicates: 7 ways to know a turn is running; 2 optimistic-sent-message mechanisms; 4 message stores; 3 follow-up triggers with separate counters; 3 progress estimators; "built" detected 4 ways.

## 3. Cross-cutting patterns

1. **State that matters lives in memory with a checkpoint file beside it** (script job, share chain, turn flags, lock attempts, note requeue, sub-agent cards). Every restart story in the feedback log is this.
2. **Fallbacks instead of diagnosis** (export chain, pieced→whole proxy, hardware→libx264, stall restarts with the same inputs, silent `catch(() => {})` ×122).
3. **Shared resources without an owner**: the hardware encoder, the uplink, the lock, "is this Mac busy".
4. **Timers as design**: 285 timers; the ones that interact (idle release 60 s vs heartbeat 75 s, quit 5 s vs Convex 15 s, pace judge vs encoder contention, after-turn render 45 s vs follow-ups) were set independently.
5. **The same concept implemented twice or more** everywhere a feature was rebuilt rather than replaced: players, proxy forms, sync systems, job ledgers, busy rules, progress estimators, export lists.
6. **Operational dependencies with no product-level alarm**: ElevenLabs credit, relay reachability, disk room, Claude plan.

## 4. Proposed scope (one sub-agent per item, after agreement)

Each item ships on its own, measured before and after, with tests, and removes what it replaces. Order: A first (the team's pain), then B and C (the restart and conflict webs), then D to H.

A. Playback, one owner: native player v2 (native clock, decode-ahead, native sound, deltas over IPC, whole local copies only, prefetch on open), retire smooth/scrub/blocks on the Mac, keep the page path for browsers and Linux behind one switchable interface; measure before and after on the Mac with the three scenarios above.
B. One durable job table (jobs, turns, shares, retries) with idempotency keys and one resumer; the share as a persisted state machine; `busyWith` reads it.
C. One sync core for projects and scripts (lock by presence, persistent monotonic revs, conflicted copies visible team-wide); agent writes through one rev-checked path; hand edits locked out during a turn or merged field-wise, decided once.
D. One encoder lease (export > share copy > playback > ahead > proxies), and pace judges that know about it.
E. Verification by decoding, not metadata, shared by export join, review copy and worker.
F. Import: persisted per-file job state, one footage pipeline, one proxy kind, bounded steps, import "done" decoupled from voices/research; quota-exhaustion queues and alerts instead of failing.
G. Page hygiene: selected store subscriptions, memoised turns, media status batched, turn-end cascade fixed with a reproducible test; `e.clips` null and #185 located from the nightly-59+ logged locations.
H. Delete the dead or superseded: Modal-era whole-file smooth path, CutPlayer remnants, duplicate lists/estimators, unused `EDIT_*` flags.
I. Acceptance and release gates (from the second audit, section 5): real-Mac end-to-end checks of cold and warm footage, cuts, scrubbing, full screen, Script mode, disconnects, sleep/wake and concurrent work, run on the tagged commit; the release workflow depends on them and on the Check workflow for both platforms, so a nightly tagged on Linux can't publish past a Mac failure.

The second audit's four workstreams map onto these: "Media availability and playback" = A (+ the cleaner and pieces rules in 5.1, 5.2); "Save and job durability" = B + C (+ 5.7, 5.8, 5.9); "Shared resource scheduling" = D (+ 5.4); "End-to-end acceptance and release gates" = I. Its "fix the reproduced data-loss and cleanup defects first" ordering is adopted: 5.1, 5.7, 5.8 are small, reproduced, and go before A starts.

Where the native time goes: compositing (p50 0.8 ms) and presenting (0.3 ms) are never the limit; decoding is. Of the slow frames' time, 96% is decoding: 206 seeks took 6.5 s, 198 decoder opens 0.67 s, and 4 FFmpeg reads 2.0 s. One AVAssetReader seek on a local whole proxy costs 20–450 ms (p50 ~75), and an open 2–120 ms. Defects the trace found (both go into stage 1):

- **Silent native playback.** `tick()` skips `warm()` in native mode, and `warm()` is the only place sound is asked for while playing. Native sound is only what was decoded while the playhead rested.
- **A decoder opened every frame.** With two video layers on screen, `decode_all` replaces the share's reader with a fresh `VideoReader::open` when the file or size changes, instead of taking one from the pool. That's 473 opens and 490 seeks in 160 s for 30 cuts, and it's why p90 sits at 20 ms.

Also found: 147 of the 242 picture sources are own-file proxies (the proxy key is an `edit/originals/…` object: maps, interview cuts), plus 55 images. `native_preview.ts` fetches only `edit/proxies/` keys whole, so those stay loopback FFmpeg streams for good.

## 5. The second audit (Nov 8, another agent's pass), merged

A second read-only audit ran 105 existing tests (all passed) and reproduced four failures in isolation. Its findings, with my verification against the code (Nov 8). Where the two audits overlap the point is kept once here and cross-referenced.

1. **The cleaner deletes the local footage copies the native player needs.** Reproduced by the second audit; confirmed by me in code and by the Mac sweep (section 0: `cache/cloud/proxies` 0 bytes, the same whole preview fetched up to 8 times). `cache_cleanup.ts:159-185`: every `edit/proxies/` copy whose size matches R2's HEAD is removed, skipping only directly referenced paths, pending `upload` jobs and uploads in flight; no age, budget or "the native player chose this" check. Runs 10 min after start and hourly. The existing cleanup test expects this. This is the Oct 29 "everything on the cloud!" policy colliding with the Nov 6 "play from local footage" implementation; it can also leave the player holding a path that no longer exists. Fix before A: the cleaner keeps whole copies the native player or the agent's renders selected, and evicts them only by the cache budget, oldest-opened project first.
2. **Long videos bypass the whole-proxy download.** Confirmed: `native_preview.ts:30-38` fetches whole only keys under `edit/proxies/`; pieced proxies (`edit/pieces/v3/…`, every video of 20 min or more) stay loopback streams through `cloud_media.ts:1584-1596` (`pieces.serve`), where a seek may first fetch or make the piece. "Native player on" does not mean "local, seek-ready footage". Pieces need a local form the player can read directly (the pieces themselves are files; the player should read them, not the HTTP path).
3. **The native player draws on demand without preparing upcoming cuts.** Same as section 1 items 1 and 2; the second audit adds that native also switches smooth renders off (`playback.ts:233`, `Viewer.tsx:117`), so a slow native path loses that alternative without an error. Needs a scheduler: prepare upcoming sources, bounded decoded-frame queues, cancel obsolete seeks, presentation coordinated with the audio clock.
4. **Playback has no reliable priority over background work.** Confirmed as policy: exports made ahead yield to requested exports and smooth renders (`export_ahead.ts:84-109`) but native playback sends no signal, so they start while someone watches an unchanged timeline; `noRoom` (`export_capacity.ts:97-99`) returns null when nothing runs, so the first export skips the memory and CPU checks (by design, but it means the viewer's Mac can be loaded by one export at any time); whole-proxy downloads have their own queue (`local_previews.ts:27-37`) outside the viewer-priority mechanism. Impact needs measuring. Belongs to D.
5. **Native doesn't cover every place the team watches.** Confirmed: Script mode uses the browser decoder (`writer/playback.ts`), full screen turns native off (`Viewer.tsx:160`), five failures disable it for the session and a refused open sets `nativeRefused` until reload (`playback.ts:371-392, 481-488`), and it needs Edit.app's window (`nativePreview.ts:19`). Reports don't measure native frame delivery (`recordTiming("preview: native", 0)` marks the first open only) or explain path transitions. A on coverage; G on reporting.
6. **A rejected native project update leaves the previous picture active.** Confirmed: `preview_project` answers once the command is queued; the player thread's `set_project` error is `eprintln!`ed, never returned (`crates/edit-window/src/preview.rs:95-100`), and the player keeps the last accepted project. The timeline can change while the window still draws an older state. Fix in A: revision acknowledgements for project acceptance and for drawn frames.
7. **Leaving the editor after failed saves loses unsaved changes.** Reproduced by the second audit (offline: three failed saves, then `project: null`, no undo entries, `dirty: false`); confirmed in code: `web store.ts:502-517` flushes three times, toasts "Your last changes couldn't be saved." and closes anyway. Unsaved work needs a durable local copy before navigation discards it. Goes before A, into B/C.
8. **Restart recovery can lose the jobs it recovers.** Reproduced; confirmed: `jobs.ts:108-112` `takeOver` writes `[]` before starting the resumers, so a second crash during recovery, or a resumer that throws before re-registering, leaves no durable job. Recovery should claim jobs one at a time and keep each until it ends or fails for good. Part of B; goes before A.
9. **Ideas and Thumbnails can finish locally and stay "running" in the cloud.** Confirmed: when saving the ending fails, both warn and delete the local run (`ideas/run.ts:721-726`, `thumbnails/run.ts:900-904`) with no durable pending completion to retry; the page keeps the old cloud state. Thumbnail ownership treats another holder's run as live for 20 min (`thumbnails/run.ts:841`) while a turn may run 25 min (`:875`) plus queue time, with no renewed lease. Needs durable completion records and renewable ownership. Part of B.
10. **The review-copy validator accepts missing audio.** Reproduced; confirmed: `review_check.ts:45-51` checks the sound only when the copy reports one, so a copy with picture and no sound passes even when the export had sound. Same class as section 2c's "lengths only". Part of E.
11. **Release publication doesn't require the Mac CI checks.** Confirmed: `release.yml` runs on tag push and has no dependency on the Check workflow (`on: push: tags`, jobs `prepare → web → build → upload → publish`); `just nightly` runs `just check` locally first (`Justfile:213`), which on Linux never exercises the Mac window or AVFoundation paths. A nightly tagged from Linux can publish regardless of the Mac Check result. Part of I.

The second audit's operational notes agree with section 0 (JJ's 65.8 s cloud-preview request, Marc on the page/smooth path, JJ's backend unknown until today's `ui: preview: native`). Its Mac decode numbers are in section 4. Its reading of the history matches mine: WebCodecs workers → block cache → smooth renders → pieced proxies → native drawing accumulated, and the policies around them (cleanup, restart handling, completion handling) were never replaced to match.
