## How to delete, when it's time

1. Run the audit again (below): never act on these numbers or an old key list.
2. Footage (originals, proxies, pieces, excerpts) goes through Repack's Projects-page archive, or the same steps: delete the files, mark their `editMedia` rows not ready, record what was freed so it can be restored. Deleting an original without its registry row means the next import of that Drive or YouTube file reuses a key that's gone.
3. Originals from someone's disk (`edit/originals/sha256/…`, 46 GB of the finished ones) can't be fetched again; 17.8 GB of them are their own only proxy. Drive and YouTube originals can (54 GB). Exports read originals, so re-exporting a project whose originals went downloads them first.
4. Review files: keep each project's latest version (its link plays), close a review before deleting its files.
5. Temporary prefixes (`edit/test/`, `edit/exports/results/`, `edit/reviews/tmp/`, `edit/transcribe/`, `edit/proxies/jobs/`): an R2 lifecycle rule deleting objects older than 7 days under each stops them piling up again (`npx wrangler r2 bucket lifecycle add foia-render-results …` once per prefix). Adding it deletes what's there, so it waits for the go too.
6. Never run `app/scripts/cloud-sweep.ts --delete` from a version before Nov 11: it read only Writer's Convex rows, which name no footage, so it would have deleted the 83.7 GB of originals live Writer scripts hold. (Fixed on Nov 11: below.)

## What stops it growing (built Nov 11)

- **Old review versions go.** Sharing a new version of an Edit review retires the older ones as approving one does: their rows stay with every note, their files go to the cleanup queue. Nothing emptied that queue (nobody approved, and Repack's server was the one meant to); the relay now empties Edit's own entries.
- **Exports aren't stored twice.** A review's full-quality download points at the export's archive in the cloud when it's there, instead of uploading the same file again under `edit/reviews/` (also one whole upload less on a slow line: JJ's 8 Mbit/s).
- **The sweep counts Writer's footage** and writes nothing when it only reports.

On dev now (mamagi and the relay deployed Nov 11). Prod needs mamagi deployed (`bun run mamagi:deploy` in ~/Documents/code/accounts) and a nightly for the relay and Edit, on Sphe's go. Once mamagi is on prod, the next share of each review retires its older versions: 239 GB goes over the following days, as each project is shared again (existing reviews aren't swept on their own).

Not yet: archiving a Done project's footage by itself after a while (a policy for Sphe), the lifecycle rule above, and the second upload of a shared export (the archive goes up, then the review's copy): R2 copies within itself only up to 5 GB in one request, and JJ's exports are 5–7 GB.

## Running the audit

Read-only throughout (LIST on R2, `convex data` and the read-only `edit:getProject` on Convex). From a folder `D`:

1. R2 listing: the R2_* secrets from infisical (`--env=prod --path=/edit-relay`) in the environment, `bun app/scripts/r2-audit/list.ts D/r2.tsv`.
2. Convex dumps into `D/cx/<table>.jsonl` (editProjects, editLater, editLocks, editMedia, editNotes, reviews, reviewVersions, writerScripts, ideas, thumbnails, thumbnailAssets, projectSizes, cleanup): `cd ~/Documents/code/accounts && infisical run --env=prod --path=/mamagi -- bunx convex data <table> --limit 50000 --format jsonLines > D/cx/<table>.jsonl` (analyze.py reads editMedia from `editMedia.16000.jsonl`).
3. Project bodies: `bun app/scripts/r2-audit/bodies.ts D` (CONVEX_URL and CONVEX_SERVICE_TOKEN from the same infisical path).
4. `python3 app/scripts/r2-audit/analyze.py D`, then `python3 app/scripts/r2-audit/report.py D`: the tiers, the CSVs and the key lists.
